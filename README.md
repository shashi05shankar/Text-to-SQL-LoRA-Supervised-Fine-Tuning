# Text-to-SQL by LoRA fine-tuning

LoRA supervised fine-tuning of **Qwen2.5-1.5B-Instruct** to write SQL, measured by
**execution accuracy on Spider's held-out dev set** — 1,034 questions over 20 databases
that appear nowhere in training.

**Execution accuracy 41.0% → 65.5%** on 1,034 held-out questions, after training 1.2% of
the model's parameters for 4.2 hours on one free Kaggle T4.

Every number below is read out of `artifacts/metrics.json`, written by that run, and
spliced into this file by `scripts/report.py`. Nothing is estimated or typed in by hand —
`python scripts/report.py --check README.md` fails if any figure here drifts from the
artifact.

---

## The question this project answers

*Does parameter-efficient fine-tuning actually make a small open model better at a
structured task, and by how much — measured in a way you cannot argue with?*

"It sounds better" is not an answer. So the task is text-to-SQL, where correctness is
decided by a computer: run the predicted query and the gold query against the real
database and compare the rows that come back.

## Reading the results

**Fine-tuning fixed 308 questions and broke 55** — a net +253, and a 5.6:1 ratio. That
matters more than the headline average, because an average can hide a model that trades
one set of errors for another.

**Invalid SQL more than halved: 32.4% → 15.0%.** A third of the base model's answers did
not run at all — hallucinated columns, `misuse of aggregate function COUNT()`, bare syntax
errors. Much of what fine-tuning bought was simply learning to emit SQL that executes
against the schema it was given.

**Every one of the 20 dev databases improved or held**; none regressed. The gain is
broad, not one easy database carrying the average. Biggest:
`student_transcripts_tracking` +37.2 points, `battle_death` +37.5. Hardest remaining:
`car_1` at 37.0% and `world_1` at 40.0%.

**The gain is largest where the queries are hardest.** On the `extra` bucket
(nesting, set operations, 2+ joins) accuracy more than doubled, 22.3% → 46.6%. A gain
concentrated in `easy` would have been much less interesting.

**Few-shot prompting bought almost nothing: 41.0% → 41.2%.** Three in-context examples
moved execution accuracy by 0.2 points — while raising exact match from 11.0% to 17.2%.
So the demonstrations taught the base model Spider's *output style* without teaching it to
write more correct queries. This is the single most useful number for defending the
project: the improvement is not something a better prompt would have achieved.

### One question, end to end

Served live from the API, base and fine-tuned generated from the *same* loaded weights
with the adapter switched off and on:

> **"What are all distinct countries where singers above age 20 are from?"** (`concert_singer`)

```sql
-- base, zero-shot
SELECT DISTINCT T1.Country FROM singer AS T1
  JOIN singer_in_concert AS T2 ON T1.Singer_ID = T2.Singer_ID
  WHERE T1.Age > 20;
-- -> [('United States',), ('France',)]

-- LoRA fine-tuned
SELECT DISTINCT country FROM singer WHERE age > 20;
-- -> [('Netherlands',), ('United States',), ('France',)]   matches gold
```

The base model's answer is *plausible* and *executes cleanly* — and it is wrong. The
question never mentions concerts, but it joined to `singer_in_concert` anyway, which
silently drops any singer who has not performed at one. Netherlands disappears.

This is why the metric is execution accuracy and not a similarity score or a human
eyeball. Nothing about that query looks broken; only running it reveals the missing row.

### Two findings that cut against the result

**Validation loss rose while accuracy kept improving.** Held-out loss bottomed at ~0.213
around step 400 and climbed steadily to 0.287 by step 1100, while training loss fell from
0.545 to 0.015 — textbook overfitting. Execution accuracy was still 65.5% at the end.
Token-level cross-entropy and execution correctness are not the same objective: the model
was getting worse at reproducing Spider's exact token sequences while still producing
queries that return the right rows. Selecting on loss would have stopped this run at
roughly one epoch. Whether that checkpoint would have scored *better* on execution
accuracy is untested — checkpoints were not kept, which is a genuine limitation of this
run.

**The regressions have a pattern, and it is Spider-shaped.** Of the 55 questions
fine-tuning broke, most fail because the model adopted Spider's *stylistic* conventions
too literally — lowercase identifiers, `T1`/`T2` aliases — and then invented column names
that fit that style rather than the actual schema: `pet_type` where the schema says
`petType`. One case swapped a correct literal `'France'` for `'French'`. The model learned
the corpus's surface form alongside the task, which is exactly what SFT on a single
narrow dataset does.

## The task and the data

Given a natural-language question and a database schema, generate the SQL that answers it.

| Piece | Source | Notes |
| --- | --- | --- |
| Question/SQL pairs | [`xlangai/spider`](https://huggingface.co/datasets/xlangai/spider) | 7,000 train / 1,034 dev. Parquet. **No databases.** |
| SQLite databases + `tables.json` | [`HAL-9001/spider-databases`](https://huggingface.co/datasets/HAL-9001/spider-databases) | `spider_data.zip`, ~206 MB. Required for execution. |

Both public, both ungated, no Hugging Face token needed.

**Why Spider rather than WikiSQL.** Spider's dev databases are disjoint from its training
databases — verified in this repo, not assumed. The number therefore measures
generalization to *schemas the model has never seen*, which is the realistic condition and
the harder claim. WikiSQL is single-table and templated; a good score on it is much easier
to get and much easier to dismiss.

## The metric

Primary: **execution accuracy**. Run gold and prediction against the real database; correct
iff the returned rows match. The comparison rules are choices, so they are stated:

- Rows compare as **multisets** — order-insensitive — *unless the gold query has
  `ORDER BY`*, in which case order is part of the answer. SQL result order is undefined
  without `ORDER BY`, so demanding it would fail correct predictions for no reason.
- Duplicate rows count. A set comparison would wrongly accept a prediction that lost them.
- Column order is significant.
- Floats are rounded before comparison (SQLite's `AVG`/`SUM` vary in trailing digits with
  summation order — something neither model controls).
- A **timeout is a wrong answer, not a skipped one**; otherwise emitting non-terminating
  SQL would be a way to dodge being marked incorrect.
- Predictions that fail to execute score zero and are *also* reported as an **invalid-SQL
  rate**, tracked separately because it is where an un-fine-tuned model tends to look worst.
- Databases are opened **read-only**, so a hallucinated `DROP TABLE` cannot corrupt the
  corpus mid-evaluation.

This is a set-comparison reimplementation of execution accuracy, **not** Yale's official
test-suite EX (which re-runs against perturbed databases to catch predictions that match by
coincidence). Ours is slightly more permissive in absolute terms. It is applied identically
to every system compared, so the *delta* — the number this project reports — is unaffected.

Secondary: exact match on normalized SQL, and a breakdown by a component-count hardness
bucket. That bucketing is **our own heuristic**, not Yale's official hardness definition,
and is labelled as such wherever it appears.

## Evaluation design

Three systems, the **same** 1,034 dev questions, the same prompt builder, greedy decoding
throughout:

1. **Base, zero-shot** — no adapter.
2. **Base, 3-shot** — same prompt plus three fixed, seeded in-context demonstrations.
3. **LoRA fine-tuned, zero-shot.**

The few-shot baseline exists to pre-empt the obvious objection. Two data points invite
"your baseline was a strawman"; three answer it.

**Spider dev is touched exactly once**, at the end, for all three systems. Training-time
monitoring uses a validation split carved out of the 7,000 training examples and split **by
database**, so no schema sits on both sides — a row-wise shuffle would let val loss measure
schema memorization and look far healthier than dev accuracy ever turns out to be.

## Method

Base weights stay frozen and 4-bit quantized (QLoRA). For each targeted projection
`W (d×k)`, LoRA learns `A (r×k)` and `B (d×r)`, and the forward pass becomes
`W·x + (α/r)·B·A·x`. Only `A` and `B` receive gradients.

| | |
| --- | --- |
| Base model | `Qwen/Qwen2.5-1.5B-Instruct` — Apache-2.0, ungated |
| Adapted modules | `q,k,v,o,gate,up,down_proj`, r=16, α=32, dropout 0.05 |
| Quantization | 4-bit NF4, double quant, fp16 compute |
| Sequence length | 1024 (measured: truncates 2.6% of training examples) |
| Batch | 2 per device × 8 accumulation = 16 effective |
| VRAM budget | **≤ 8 GB** — ran on one Kaggle T4 with headroom |
| Actual run | 1,170 steps, 3 epochs, **4.2 h** on a single T4 |

Training is plain SFT on (prompt → target) pairs with **loss on the completion only**:
prompt tokens are masked to `-100`. That masking is implemented here as a pure function
and unit-tested directly, because getting it backwards trains the model to reproduce
schemas instead of writing SQL — and nothing crashes when you do. The loss curve looks
fine and the evaluation is a disaster.

`transformers.Trainer` + `peft`, rather than TRL's `SFTTrainer`: more robust to library
version drift on Kaggle, and it makes the masking our own testable code rather than a
framework detail.

fp16 rather than bf16 throughout, because the Kaggle T4 is Turing-class (compute
capability 7.5) and bf16 needs 8.0+.

**Training is pinned to one GPU.** A Kaggle "T4 x2" session exposes two devices, and
`Trainer` silently wraps the model in `nn.DataParallel` whenever it sees more than one.
DataParallel replicates the model per step, and a bitsandbytes 4-bit layer does not
survive replication — its quantization state is left behind and the first `gemm_4bit`
call dies with `CUDA error: an illegal memory access`, six frames deep in bnb and saying
nothing about the cause. The run is sized for a single device anyway, so it forces
`_n_gpu = 1`. Real multi-GPU QLoRA needs DDP, which is out of scope here.

**DPO/RLHF is not implemented here.** This is supervised fine-tuning. Preference
optimization is a documented next step, not a silent omission.

## Compute split

Training does not run locally.

- **Local (CPU, this repo):** data prep, the eval harness and metric, inference, API,
  Streamlit, tests, Docker.
- **Kaggle T4:** LoRA training and the three evaluation passes, producing the LoRA adapter
  and `artifacts/metrics.json`.

Local generation loads base + adapter on CPU and is slow. **Measured on an 8 GB laptop:
23–35 s per query**, plus ~40 s one-off model load. That is expected, not a defect, and it
is why the demo defaults to a replay view of saved predictions.

One measurement worth recording, because the naive answer is wrong. At float32 the same
query took **369 seconds** — the 1.5B model needs ~6.2 GB of weights, the machine had
0.4 GB free, and it was paging to disk. Loading in bfloat16 halves the weights to ~3.1 GB,
they fit in RAM, and the query drops to **23 s: a 16× speedup**. The usual advice that
"CPU bf16 is slower than fp32" is about arithmetic throughput and only holds once the
weights fit; when they do not, memory traffic dominates everything else. Serving therefore
defaults to bfloat16, overridable with `T2S_SERVING_DTYPE=float32`.

Note that serving dtype does perturb greedy decoding slightly — the same question produced
`COUNT(DISTINCT Singer_ID)` at fp32 and `COUNT(*)` at bf16 (both correct, both returning 6).
The reported metrics are unaffected: they are computed in a single GPU run where all three
systems share one dtype and one decoding path.

## Deployment

**FastAPI** — `POST /generate` takes a question plus either a Spider `db_id` or raw
`CREATE TABLE` text, and returns SQL. `use_adapter: false` serves the untouched base model
from the *same loaded weights*, and `execute: true` runs the result against the real
database. `POST /compare` returns both systems for one input. `GET /metrics` serves
`artifacts/metrics.json` — and 404s before a training run has been ingested, because the
API never invents numbers.

**Streamlit** — two tabs. *Replay* browses all 1,034 dev questions with every system's
prediction already computed, so comparisons are instant and are the same predictions the
headline was computed from. *Live* generates from a typed question, and says plainly that
CPU generation takes tens of seconds.

**Docker** — `api` + `ui`, with `artifacts/` and `data/` mounted read-only and a named
volume for the Hub cache so the 3 GB base model downloads once. Trained weights live
outside the image: the adapter is the output of a run, not part of the code.

```

  eval/            execution, metrics, harness    <- the metric lives here, once
  models/          base+adapter loading, and a stub for CPU tests
  train/           LoRA SFT; imported by the notebook, never run locally
  api/  frontend/  FastAPI service and Streamlit demo
tests/             mirrors src/
scripts/           download_data, measure_lengths, check_harness, smoke_local, report
notebooks/         the Kaggle training notebook
docs/kaggle_run.md the GPU handoff: what to attach, what to download, where it goes
```

The Kaggle notebook imports `text2sql_lora.eval` from this repo rather than redefining
anything. There is exactly one implementation of the metric, and the tests cover it.

`scripts/report.py` writes the results tables into this README between generated markers;
`--check` re-renders and fails if anything drifted. That is the mechanism behind the rule
that no number appears here that did not come out of a real run — and it is itself tested,
by tampering with a number and asserting the check fails.

## Known limitations

- **No checkpoint selection.** `save_strategy="no"`, so only the final adapter exists.
  Validation loss says an earlier checkpoint may have been better; that is untested and
  the run cannot be re-cut without retraining. The fix is to checkpoint and select on
  *execution accuracy* over a held-out slice of training databases — not on loss, which
  this run showed points the wrong way.
- **The model absorbed Spider's surface conventions**, not just the task. The regression
  analysis above shows invented column names in Spider's naming style. A model trained on
  one corpus in one format will do this; measuring it would need a second, differently
  formatted text-to-SQL set.
- Execution accuracy here is set-comparison, not Yale's official test-suite EX. Stated
  above; applied identically to all three systems, so the delta is unaffected.
- Schemas are serialized without example column values. Including them is known to help
  and is the most obvious next improvement — several regressions were literal-value
  errors (`'France'` → `'French'`) that example values would likely prevent.
- Spider's *test* split is hidden behind the official leaderboard, so dev is the held-out
  set — as it is in essentially every published Spider result.
- SFT only. DPO/RLHF is deliberately out of scope, not overlooked. A preference pair
  built from *executed* outcomes (correct vs incorrect query for the same question) is
  the natural next step, and this repo already produces exactly that data in
  `predictions.jsonl`.
